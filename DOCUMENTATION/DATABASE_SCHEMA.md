# Database Schema

This document describes the database schema used by the Prospect Pro application. The application uses PostgreSQL as its database system and Sequelize as its Object-Relational Mapper (ORM).

## Introduction

Models are defined in `src/models/components/` and loaded dynamically by `src/models/index.js`. This file also handles the setup of associations between models. The database connection itself is managed by `db.js`, which also ensures the database specified in the configuration exists and synchronizes the Sequelize models with the database schema using `sequelize.sync({ force: false })`.

Primary keys for all tables are UUIDs, generated automatically. Timestamps (`createdAt`, `updatedAt`) are generally enabled for all tables.

## Models

---

### 1. Users
*   **Table Name:** `Users` (Sequelize default) or as specified if `tableName` option is used (e.g., `users` by convention). The model name is `Users`.
*   **Description:** Stores user account information, roles, and status.

| Field                   | Data Type                                       | Constraints & Description                                     |
| :---------------------- | :---------------------------------------------- | :------------------------------------------------------------ |
| `id`                    | `UUID`                                          | Primary Key, Default: `UUIDV4`                                |
| `email`                 | `STRING`                                        | Not Null, Unique, Validated as Email                          |
| `password`              | `STRING`                                        | Not Null (stored as a hash)                                   |
| `token`                 | `STRING`                                        | Not Null, Unique. A JWT generated for the user upon validation (distinct from session tokens). |
| `status`                | `ENUM('UNVERIFIED', 'VERIFIED', 'ARCHIVED', 'BLOCKED')` | Not Null, Default: `'UNVERIFIED'`                             |
| `role`                  | `ENUM('USER', 'ADMIN', 'SUPER_ADMIN')`          | Not Null, Default: `'USER'`                                   |
| `reset_token`           | `STRING`                                        | Nullable. Stores token for password reset.                    |
| `reset_token_expires_at`| `DATE`                                          | Nullable. Expiry time for `reset_token`.                      |
| `createdAt`             | `DATE`                                          | Auto-generated by Sequelize                                   |
| `updatedAt`             | `DATE`                                          | Auto-generated by Sequelize                                   |

*   **Hooks:**
    *   `beforeValidate`: Generates `id` (if not present) and a user-specific `token` (JWT).
    *   `beforeCreate`: Hashes the `password` using bcrypt.
*   **Instance Methods:**
    *   `generateTokens()`: Generates JWT `accessToken` and `refreshToken` for session management.
    *   `verifyPassword(password)`: Compares a given plain password with the stored hashed password.
*   **Associations:**
    *   HasMany `Sessions` (as `sessions`, `foreignKey: 'user_id'`, `onDelete: 'CASCADE'`)
    *   HasOne `Profiles` (as `profile`, `foreignKey: 'user_id'`, `onDelete: 'CASCADE'`)
    *   HasMany `EnrichJobs` (via `EnrichJobs.belongsTo(Users)`)
    *   HasMany `ScrapingJobs` (via `ScrapingJobs.belongsTo(Users)`)

### 4. ScrapingJobs
*   **Table Name:** `scraping_jobs`
*   **Description:** Stores information about web scraping jobs initiated by users.

| Field       | Data Type                                       | Constraints & Description                                     |
| :---------- | :---------------------------------------------- | :------------------------------------------------------------ |
| `id`        | `UUID`                                          | Primary Key, Default: `UUIDV4`                                |
| `user_id`   | `UUID`                                          | Not Null, Foreign Key referencing `Users.id`                  |
| `source`    | `STRING`                                        | Not Null (e.g., "google-maps", "pappers")                     |
| `query`     | `STRING`                                        | Not Null, Validated length [1, 255] (Search query)            |
| `location`  | `STRING`                                        | Nullable (Location for the search query)                      |
| `results`   | `INTEGER`                                       | Not Null, Default: `10` (Number of results found/processed)   |
| `limite`    | `INTEGER`                                       | Nullable, Default: `0` (Limit on results to fetch by scraper) |
| `status`    | `ENUM('pending', 'running', 'completed', 'failed')` | Not Null, Default: `'pending'`                                |
| `createdAt` | `DATE`                                          | Auto-generated by Sequelize                                   |
| `updatedAt` | `DATE`                                          | Auto-generated by Sequelize                                   |

*   **Associations:**
    *   BelongsTo `Users` (as `user`, `foreignKey: 'user_id'`, `onDelete: 'CASCADE'`)
    *   HasOne `JobResult` (as `scraping_job_results`, `foreignKey: 'id'`). *Note: This implies a 1-to-1 relationship using the same PK. This is unusual; typically, a job would have many results via a dedicated FK in `JobResult` referencing `ScrapingJobs.id`.*

### 6. JobResult (Scraping Job Results)
*   **Table Name:** `scraping_job_results`
*   **Description:** Stores the actual JSON data payload from a scraping job.
*   **Note on Association:** The `foreignKey: 'id'` in its association with `scraping_jobs` is unconventional for a one-to-many relationship. It implies that the `id` of a `scraping_job_results` record is the same as the `id` of the corresponding `scraping_jobs` record, effectively making it a one-to-one relationship for storing the *entire result set* of a job as a single JSON object. If individual scraped items were to be stored, a different structure (e.g., a `scraping_job_id` FK and one row per item) would be more typical. The current structure suggests the `result` field holds an array or a large JSON object containing all findings for that one job.

| Field       | Data Type | Constraints & Description                                     |
| :---------- | :-------- | :------------------------------------------------------------ |
| `id`        | `UUID`    | Primary Key, Default: `UUIDV4`. **This ID is also the Foreign Key to `scraping_jobs.id`**. |
| `result`    | `JSON`    | Not Null (Stores the scraped data, likely an array of objects) |
| `createdAt` | `DATE`    | Auto-generated by Sequelize                                   |
| `updatedAt` | `DATE`    | Auto-generated by Sequelize                                   |

*   **Associations:**
    *   BelongsTo `scraping_jobs` (as `scraping_job`, `foreignKey: 'id'`, `onDelete: 'CASCADE'`). Links this result set to the parent scraping job.
